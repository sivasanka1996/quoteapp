# PI-9 → PI-12 — design

*Written 2026-08-17. Companion to `CLAUDE.md`, which stays the plan of record.*

Four independent subsystems, in value-to-Dad order. Each task below is sized to
**one session: one coherent change, its tests, one commit.** Nothing here needs
a console login, a deploy, or a photograph — that is deliberate, and it is why
these four were chosen over anything in `HUMAN-TASKS.md`.

---

## §0 — What this is answering

PI-1 through PI-8 are built. The audit on 2026-08-17 found the remaining
buildable work falls into four groups, and one of them is not a feature at all:

1. **Dad retypes the same items constantly.** He is a middleman quoting a
   similar basket to several customers. Nothing in the app copies a quote.
2. **Voice only ever ADDS.** A mis-heard line has to be hunted down and fixed by
   hand, and there is no undo after a voice or image import drops rows in.
3. **PI-8 left two edges unfinished** — pages cannot be reordered, and a long
   read starts N sequential model calls with no warning.
4. **Roughly 88 browser checks recorded in `CLAUDE.md` cannot be re-run.** The
   Playwright harnesses were never committed. Every claim about `ImageReader`,
   `VoiceReader`, `QuoteEditor` and the customer-edit sheet rests on a run
   nobody can repeat.

Item 4 is the one with no direct value to Dad and the highest cost if ignored.
It is scheduled last so the three features land first, but it is not optional.

### What is deliberately NOT here

- **PDF upload for slips.** Dad photographs handwritten paper. A supplier PDF is
  a speculative input, and `pdf.js` is a real dependency to carry for it. YAGNI.
- **Delete a customer.** Still deliberately absent — see KNOWN GAPS in
  `CLAUDE.md`. Nothing is asking for it.
- **Bug #9.** Self-healing, only ever toward correctness. Not worth a migration.
- **Anything from `HUMAN-TASKS.md`.** That queue is drained last, by a person.

## §1 — PI-9: Duplicate a quote

### The problem

`useQuotes` exposes `saveQuote`, `setStatus` and `deleteQuote`. There is no way
to base a new quote on an old one. Dad quotes the same eight items to five
customers and types them five times.

### Against the locked "no price memory" decision

`CLAUDE.md` locks *"No inventory, no product catalog, no price memory"*. This
does not breach it, and the distinction is worth stating because it will be
questioned later:

> A catalog is the **app inferring** what an item costs. Duplication is **Dad
> choosing a specific document** and copying it. The app learns nothing, stores
> no price index, and offers no suggestions. If he duplicates a six-month-old
> quote, he gets six-month-old prices — and that is his problem to see, not the
> app's to solve.

The one hazard is exactly that: **stale prices copied forward silently.** The
design answers it by making the copy visibly a draft with a name that says where
it came from, not by adding cleverness.

### Design

A pure `duplicateQuote(source, opts)` in `types.ts`, and a copy button in the
quote list on `CustomerScreen`.

What the copy carries and what it drops:

| Field | Behaviour | Why |
|---|---|---|
| `lines` | **Copied**, with ids re-minted from `seedNextId([], 1)` | The whole point. Fresh ids so the duplicate cannot collide with the source. |
| `name` | `"<source name> (copy)"`, or `"Copy of Untitled"` when unnamed | He must be able to tell them apart in a list where every other column matches. |
| `status` | **Reset to `"draft"`** | Copying an *accepted* quote must never produce a second accepted quote. |
| `createdAt` / `updatedAt` | **New**, minted at duplication | Drives the quote number `Q-260817-1423`. A copy is a new document, not a revision. |
| `customerId` / `customerName` | Caller's choice — same customer by default | Quoting the same basket to a different customer is the higher-value half. |
| `totalSale` | Recomputed, not copied | Denormalized field; copying it forward would reintroduce bug #9's shape. |

`duplicateQuote` is pure and returns the *arguments* for `saveQuote` rather than
writing anything itself. That keeps the Firestore write on the one tested path
that already races the ack (`firestoreAck.ts`), instead of adding a second write
site that could hang Dad's button offline.

### UI

A copy control on each row of the quote history. Tapping it opens a small sheet:
the new name (prefilled), and a customer picker defaulted to the current
customer. Confirm writes through `saveQuote` and navigates into the new quote,
so Dad lands in the editor ready to change prices.

Reuses `var(--tap)` 48px targets and the existing sheet pattern from the
customer-edit sheet — no new interaction vocabulary.

### Tasks

| # | Task | Files | Notes |
|---|---|---|---|
| 9.1 | `duplicateQuote` + tests | `types.ts`, `types.test.ts` | Pure. Covers id re-mint, status reset, name fallback, line independence (mutating the copy must not touch the source). |
| 9.2 | Copy button, sheet, customer picker | `CustomerScreen.tsx/css` | Writes via existing `saveQuote`. Navigates on success. |

### Testing

Unit tests on the pure function. The sheet gets a component test in PI-12.4 —
noted here so it is not silently dropped.

## §2 — PI-10: Voice undo and voice edit

### The problem

Two gaps, one small and one real.

`handleAddFromVoice` ([QuoteEditor.tsx:188](../../../src/QuoteEditor.tsx#L188))
and `handleAddFromImage` ([QuoteEditor.tsx:204](../../../src/QuoteEditor.tsx#L204))
both append to `lines`. If a read drops eight wrong rows in, Dad deletes eight
rows by hand.

And voice **only adds**. There is no way to say *"change the wire rate to
1800"* — he must find the line and open its edit sheet.

### Design — 10.1 undo

A single-step undo. Before either handler appends, snapshot the current `lines`
into `lastImport` state along with a label ("8 items from image"). Render an
undo affordance near the item list while a snapshot exists; tapping it restores
the snapshot and clears it.

Deliberately **one step, not a stack.** The failure being solved is "that import
was wrong, take it back" — which happens immediately, once. An undo stack means
deciding what else enters it (blanket discounts? line edits? deletes?), and that
is a much larger design for a smaller benefit.

The snapshot clears on save, so undo can never resurrect lines across a save
boundary and contradict what Firestore holds.

### Design — 10.2 voice edit

`voiceParse` is already a tokenizer (PI-6): tokenize → classify → assemble. This
adds an **intent** stage between classify and assemble.

Two intents:

- `ADD` — today's behaviour, and the default. Anything not clearly an edit is an
  add, because a wrongly-detected edit silently changes an existing price, while
  a wrongly-detected add leaves a visible extra row.
- `SET` — triggered by a leading change keyword (`change`, `set`, `update`, and
  the Telugu equivalents) **and** a resolvable target line **and** a field to
  set. All three, or it falls back to `ADD`.

Target resolution is fuzzy string matching over the names of lines already in
the quote — the same posture `CLAUDE.md` prescribes for item search, and for the
same reason: a few dozen strings, so Fuse.js or a plain scorer, never embeddings.

**An ambiguous target does not guess.** If two lines match closely, the confirm
panel asks which one. The panel already exists and already shows a confirm step
before anything reaches the quote, so this is a new branch in a proven flow, not
a new flow.

`VoiceItem` grows a discriminated union so the editor's handler can tell the two
apart at the type level rather than by inspecting fields.

### Tasks

| # | Task | Files | Notes |
|---|---|---|---|
| 10.1 | One-step undo for voice and image imports | `QuoteEditor.tsx/css` | Snapshot before append; clear on save. |
| 10.2 | Intent classification `ADD` / `SET` in the parser | `voiceParse.ts`, `voiceParse.test.ts` | Pure. All 16 existing tests must pass **unchanged** — that is the acceptance condition, as it was for PI-6. |
| 10.3 | Target matching + the ambiguity branch in the panel | `VoiceReader.tsx/css`, `QuoteEditor.tsx` | Fuzzy match over existing line names. Needs the quote's lines passed into the panel. |

### Testing

10.2 is pure and fully unit-testable. 10.1 and 10.3 are component behaviour and
are covered by PI-12 — which is the argument for doing PI-12 at all, and the
reason it is scheduled in the same plan rather than "someday".

**What none of this proves:** that Chrome hears *"change the wire rate to
1800"* correctly from Dad. Recognition quality needs a microphone and a human
voice, and stays in `TESTING.md`.

## §3 — PI-11: Finish the image path

Two small edges PI-8 left open. Both are contained in `ImageReader.tsx`.

### 11.1 — Page reordering

Pages are read and badged in the order they were picked. Photograph page 3
first and every badge is wrong; the only fix today is removing pages and
re-adding them.

**▲▼ buttons on each thumbnail, not drag-and-drop.** Drag on a phone competes
with page scroll, needs long-press to disambiguate, and is hard to hit at 48px.
Two buttons are unambiguous and match the big-touch-target posture everything
else in the app follows.

The move itself is a pure `movePage(pages, from, to)` so it can be tested
without a DOM. Reordering is only offered before the read starts — reordering
*results* is a different and much larger problem, and merged rows already carry
the page they came from.

### 11.2 — Long-read guard

Pages read sequentially, one model call each (spec §5.2, and that stays). Ten
pages is ten round trips. The progress line already says "Reading page 2 of
3…", but nothing warns him *before* he commits to a long wait.

Above a threshold (6 pages, from `config/app.config.ts` like every other tunable
in this app), the read button confirms first, naming the page count and a rough
expected wait derived from the measured per-page latency (~3s from the live
runs on 2026-08-12).

Deliberately **a warning, not a cap.** A genuine ten-page order must still be
readable. The failure being prevented is a surprise, not a long read.

### Tasks

| # | Task | Files | Notes |
|---|---|---|---|
| 11.1 | `movePage` + ▲▼ controls | `parse/mergePages.ts` (or a sibling), `ImageReader.tsx/css` | Pure move, tested. Disabled at the ends. |
| 11.2 | Long-read confirmation | `ImageReader.tsx`, `config/app.config.ts` | Threshold in config, not inline — the standard this repo set on 2026-08-11. |

## §4 — PI-12: Put the browser checks in the repo

### The problem, stated plainly

`CLAUDE.md` records these verification runs:

| Run | Checks |
|---|---|
| PI-8 multi-page in the browser | 18 |
| ImageReader panel | 23 |
| VoiceReader panel | 26 |
| Customer editing | 21 |

**None of the harnesses were committed.** Each says "the harness is not in the
repo (it needs Playwright and a live Firestore)". So the checks are real
history, and they are also unrepeatable. `ImageReader.tsx` is the most intricate
component in the app — multi-page state, sequential reads, partial failure,
per-page retry preserving edits — and it has **zero automated coverage**.

The 241 unit tests are all pure functions, because `vite.config.ts` sets
`environment: 'node'` globally.

### Design

Add a **jsdom project alongside the node one** rather than switching the suite
over. Vitest 4 supports `test.projects`, so both run under one `npm test`:

- **`unit`** — `environment: 'node'`, everything that exists today, unchanged.
  The Cloudflare Worker tests in particular must stay on node; they run a
  `fetch(Request) → Response` handler and jsdom would buy them nothing.
- **`dom`** — `environment: 'jsdom'`, matching `src/**/*.dom.test.tsx`, with
  Testing Library and a setup file.

The separate glob matters: it keeps the boundary explicit, so nobody later
writes a pure test that silently depends on a DOM being present.

**These replace the throwaway Playwright harnesses only partly, and the spec
should not pretend otherwise.** Component tests render into jsdom with Firestore
and the model proxy stubbed. They can prove the panel's *logic* — page merge,
retry preserving edits, warning counts and grammar, the decimal-entry
regression. They cannot prove layout at 390px, real network behaviour, or the
service worker. Those stay human or stay in a throwaway harness. What this buys
is that **a regression in the merge or retry logic fails CI** instead of
reaching Dad.

Priority within PI-12 follows intricacy, not screen count: `ImageReader` first.

### Tasks

| # | Task | Files | Notes |
|---|---|---|---|
| 12.1 | jsdom project + Testing Library + setup | `vite.config.ts`, `package.json`, new setup file | Acceptance: all **241** existing tests still pass, and one trivial DOM test passes. |
| 12.2 | `ImageReader` component tests | new `ImageReader.dom.test.tsx` | Multi-page strip, sequential read order, partial failure, retry preserving hand edits, incomplete-row warning count **and** singular/plural grammar, decimal entry. |
| 12.3 | `VoiceReader` component tests | new | Language toggle and persistence, the `stageRef` guard both directions, error branches, alternatives re-parse. Mock `window.SpeechRecognition` as the 2026-08-07 harness did. |
| 12.4 | `QuoteEditor` + `CustomerScreen` tests | new | Undo (10.1), the duplicate sheet (9.2), no-cost warning, blanket discount. |

### Regression targets worth pinning

These are defects this codebase actually shipped once. Each becomes a test:

- Qty and rate fields must accept `2.5` keystroke by keystroke — typing `2.5`
  once produced `25` (PI-2 review).
- A retry must not discard hand edits made to rows on surviving pages (PI-8).
- A legacy `"Untitled"` quote must render no `Subject:` line (PI-2 review).

## §5 — Sequencing and risk

PI-9, PI-10 and PI-11 are independent and can be built in any order. **PI-12.1
should land before 12.2–12.4 obviously, and ideally before 10.1 and 9.2**, so
the new UI work can be tested as it is written rather than retrofitted.

Recommended order: **12.1 → 9.1 → 9.2 → 11.1 → 11.2 → 10.1 → 10.2 → 10.3 →
12.2 → 12.3 → 12.4.**

| Risk | Judgement |
|---|---|
| Duplicate carries stale prices forward | Accepted, and mitigated by the name and the forced `draft` status. Dad picks the source document; the app infers nothing. |
| Voice `SET` changes the wrong line | Mitigated by three-part gating, fuzzy match, an explicit ambiguity branch, and the existing confirm step. Default is always `ADD`. |
| jsdom project slows or destabilises the suite | Contained: separate project, separate glob, and the acceptance condition is that all 241 existing tests pass unchanged. |
| Scope creep into an undo stack | Explicitly out of scope — one step, cleared on save. |

**Nothing here changes what is deployed.** All of it lands on
`feature/Vision_Draft` and reaches Dad only through the merge and deploy that
`HUMAN-TASKS.md` §1 tracks. That is unchanged by this spec and is not a blocker
for any task in it.
